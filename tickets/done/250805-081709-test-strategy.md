## Overview

### 背景

#### ESLintのテスト設定緩和の必要性

現在のmainブランチではテストコードに対して厳格なESLintルールが適用されており、以下の問題が発生しています：

**現在の問題**：

- テストコードでの`any`型使用が制限されている
- テストヘルパー関数の戻り値型明示が必須
- destructuringでの未使用変数がエラーになる
- Node.jsグローバル変数（setTimeout, setInterval等）が未定義エラーになる

**このチケットで実施する変更**（eslint.config.js）：

```javascript
// Test files specific configuration
{
  files: ['tests/**/*.ts', 'tests/**/*.test.ts', 'tests/**/*.spec.ts'],
  rules: {
    '@typescript-eslint/no-explicit-any': 'off',
    '@typescript-eslint/explicit-function-return-type': 'off',
    '@typescript-eslint/no-unused-vars': 'off'
  }
}
```

**変更の理由**：

- テストコードではモックオブジェクトの型定義が複雑
- テストヘルパー関数の戻り値型は推論で十分
- destructuringで未使用変数が発生しやすい

#### 現在のテストの問題点

現在のテストコードには多数の失敗があり、t_wadaの診断により以下の問題が判明しました：

- 実装詳細に過度に依存したテスト設計
- privateメソッドの直接テスト
- 内部状態の詳細な検証
- パブリックAPIの振る舞いテストの不足
- モックが複雑すぎて、実際の振る舞いよりもモックの動作をテストしている

### 目的

t_wadaの推奨に基づき、以下の方針でテスト戦略を刷新します：

1. **境界テスト重視**: パブリックAPI、入出力、エラーケースに焦点
2. **振る舞いテスト**: 実装詳細ではなく、観察可能な動作をテスト
3. **仕様駆動**: @docs/spec.mdに基づいたテスト設計
4. **保守性向上**: 実装変更に強いテストコードの実現

### t_wadaからの主要アドバイス

- 現在のテストコードは全削除も検討可能
- 機械的な修正ではなく、根本的な設計見直しが必要
- 実装詳細へのアサーション（loggerへの呼び出し確認など）は削除
- publicメソッドの入出力と振る舞いに集中

#### モック使用方針

**許可されるモック:**

1. 外部API（ネットワーク通信）
2. 時間に依存する処理（Date, setTimeout）
3. ランダム性のある処理
4. 環境依存の設定（環境変数など）

**禁止されるモック:**

1. ファイルシステム全体
2. 内部モジュール
3. 同一プロジェクト内のクラス
4. Node.js標準モジュール（特別な理由なく）
